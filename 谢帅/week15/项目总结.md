# 代码审查员 Subagent 并行审查系统 — 项目总结与介绍

> 日期：2026-08-12
> 位置：`E:/study/code/week15/homework`

## 一句话介绍

给它一个代码项目目录，它会自动扫描目录、挑出关键文件，然后为每个文件派一个「审查员 AI」并行审查，最后汇总成一份结构化的代码审查报告，并配一套实时可视化界面。

## 核心思路：一个主管带一队审查员

系统模仿真实团队 code review 的组织方式，采用 **动态 Orchestrator-Workers（编排者-工人）** 范式：

```
你输入：一个项目目录
        ↓
主 agent（主审查员）
   ① 先 scan_directory 扫一遍，看有哪些代码文件
   ② 自主挑出关键文件（跳过测试、__init__ 等），派活：
        dispatch_reviewers("a.py | b.py | c.py")
                ↓
        ┌── 审查员1 读 a.py → 挑问题 ──┐
        ├── 审查员2 读 b.py → 挑问题 ──┤  同时并行跑（ThreadPool）
        └── 审查员3 读 c.py → 挑问题 ──┘
                ↓
   ③ 收齐所有审查员的结果 → 综合成一份完整报告
```

关键点：主 agent 不是按固定脚本走，而是**自己决定审几个文件、派几个审查员**——拓扑图在运行时才动态生长。

## 每个角色都是一个 ReAct 循环

系统里所有 AI（主 agent 和审查员）都跑同一套 **ReAct 引擎**（Reason + Act：思考 → 选工具 → 执行 → 观察 → 再思考），区别只在「手里有哪些工具」：

| 角色 | 工具 | 职责 |
|------|------|------|
| 主 agent | `scan_directory` + `dispatch_reviewers` | 挑文件、派活、汇总报告 |
| 审查员 subagent | `read_file` | 读一个文件，从正确性/安全/性能/可读性四个维度挑问题 |

审查员输出的每条问题格式统一：`[严重级别 高/中/低] 行号 — 问题描述 → 修复建议`。

## 为什么强调「并行」——这是设计重点

N 个文件本来要一个接一个审（串行，耗时 = 各文件之和），改成并行后耗时 ≈ 最慢那一个文件。系统内置了 `eval_compare.py` 做 **parallel vs serial A/B 对比**，跑出真实的加速倍数，用数据证明并行的价值。这是本项目最想展示的核心点，对应「subagent 并行加速」范式（Amdahl 定律：加速收益只在可并行的审查段，主 agent 的规划/汇总是串行瓶颈）。

## 几个值得说的设计取舍

1. **审查不联网**——参考项目（市场调研）每个子 agent 都要联网搜资料，但代码审查靠模型本身的知识就够。砍掉 Tavily 依赖后更稳、更快、更好演示，也不需要额外的搜索 API key。
2. **按文件拆分而非按维度拆分**——每个审查员领一个文件、全维度审。这样不受项目大小限制（项目大就多派几个审查员），也最贴近真实 code review。
3. **可视化代码与业务逻辑隔离**——SVG 拓扑动画单独放在 `topology.js`，读代码的人可以只关注 agent 逻辑，不被前端干扰。
4. **零依赖手写 ReAct**——ReAct 引擎、文件工具、拓扑图全是手写，除大模型 SDK 和 Web 框架外没引额外库。
5. **主/子 agent 共用同一个 ReAct 引擎**——区别仅在 tools 字典和 system prompt，体现「同一范式、不同装备」的清晰抽象。

## 安全与健壮性

- **路径安全**：文件访问限制在项目根目录内，防目录穿越
- **文件数上限**：最多派 8 个 reviewer，防数量爆炸
- **读取截断**：单文件最多读 400 行，防 context 过长
- **工具不抛异常**：`scan_directory`/`read_file` 出错返回错误字符串，由 ReAct 循环兜底
- **解析兜底**：LLM 不带 `Final Answer:` 前缀直接写报告时，也能正确识别，避免死循环
