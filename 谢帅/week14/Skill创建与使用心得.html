On Building Skills

重复的工作，
做成一次编写、
永久复用的 Skill

这是我用 Claude Code 做「工作总结看板」时沉淀的一份心得——关于什么该做成 Skill、自己的 Skill 如何越用越顺手、怎么把一段流程变成 Skill，以及一条不能绕过的安全底线。

共 5 篇 创建流程 3 步 用途 · 部门分享
01
Why · 复用的价值

重复的工作，一定要做成 Skill省时 · 省力 · 省 Token

同一段脚本、同一套流程，如果每次都让大模型从头写一遍，不仅慢，还要把整段逻辑反复塞进上下文——既费时间又费 Token。做成 Skill 后，脚本已经躺在 scripts/ 里，直接执行即可，不必重新生成。

背后的关键机制是渐进式披露：平时只有一句话的描述留在上下文；真正触发时才加载正文；脚本和参考文档只在需要时才读取，甚至可以只执行不读取。上下文始终精简，成本自然可控。

1 次脚本只需写一次
≈100 词平时仅占一句描述
按需正文与脚本延迟加载
02
How · 在使用中进化

自己做的 Skill，最懂自己越调越顺手

通用 Skill 只能给通用答案；自己针对自己的任务打磨出来的 Skill，才真正贴合自己的工作方式——文件命名习惯、常踩的坑、想要的输出格式，都能固化进去。

Skill 也不是写完就定稿，而是在使用中不断完善。每次实跑暴露的问题，都是一次改进机会；好的 Skill 是「用出来」的，不是「一次写死」的，慢慢就能调教成最适合自己任务的样子。

  • 实跑发现中文路径乱码 → 在脚本里加 UTF-8 修复
  • 发现某月报告缺数据 → 补一条「宁可删模块也不编造」的规则
  • 把只能用于个例的写法，泛化成对任意报告都成立的指引
03
Process · 三步创建

怎么把一段流程做成 Skill

方法很朴素：先手动把流程走通，再把这段成功的流程打包成 Skill，最后换真实输入反复迭代。

壹

带着大模型走一遍

先和大模型把完整流程手动跑通，拿到你真正想要的最终产物。

贰

用 skill-creator 打包

把刚才这段成功的流程，交给 skill-creator 插件整理成 Skill。

叁

实跑 + 迭代

换个真实输入跑一遍，根据结果反复完善，直到稳定好用。

安装 ›/plugin install skill-creator@claude-plugin-directory
04
Scale · 分而治之

复杂场景：拆成主 Skill + 子 Skill

当一个任务涉及多个领域或多条分支，不要把所有逻辑硬塞进一个 SKILL.md。主 Skill 负责判断和调度，子 Skill / 参考文档负责各自领域的细节，大模型只在需要时读取对应那一份，既清晰又省上下文。

cloud-deploy/ # 主 Skill：负责判断与调度 ├── SKILL.md └── references/ # 子模块，按需读取 ├── aws.md ├── gcp.md └── azure.md
05
Caution · 安全底线

别让 Skill 变成漏洞入口

Skill 里的脚本是会真实执行的，不像普通文档只是给人看。一个不小心，可能泄露密钥、误删数据，甚至给攻击者留后门。
泄露密钥

脚本读取 .env、凭证文件后若打印或外发，敏感信息就暴露了。

误删数据

递归删除、批量覆盖等高破坏操作，执行前务必确认范围。

留下后门

来路不明的 Skill 可能夹带恶意代码，安装前先看清它到底做了什么。

供应链风险

依赖用固定版本、选可信来源，警惕仿冒名的「李鬼」包。
