# 第十五周作业：实现一个可以下发 subagent 的 agent，并行完成多项工作

> **作业要求**：自己实现一个可以下发 subagent 的 agent，并行完成多项工作。

## 一、做了什么

实现了一个 **Orchestrator-Workers（主管-下属）多智能体系统**：一个主 Agent 负责
把复杂任务**动态拆解**成多个互相独立的子任务，然后**并行下发**给多个 subagent 同时
干活，最后把各子结果**汇总**成一份最终交付物。并用真实数据证明并行相对串行的加速。

整个系统只依赖 `openai` 包 + `DEEPSEEK_API_KEY`，**自包含、可一键运行**（不需要联网搜索等外部服务）。

## 二、架构（三步流水线）

```
用户任务
   │
   ▼
┌─────────────────────── 主 Agent (Orchestrator) ───────────────────────┐
│  1. plan()       让 LLM 把任务拆成 N 个"可并行、无依赖"的子任务(JSON)     │
│  2. dispatch()   ThreadPoolExecutor 并行跑 N 个 subagent                │
│  3. synthesize() 让 LLM 把 N 份子结果汇总成最终报告                       │
└───────────────────────────────────────────────────────────────────────┘
        │              │              │              │
        ▼              ▼              ▼              ▼
   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
   │subagent1│   │subagent2│   │subagent3│   │subagent4│   ← 各自一个 LLM 调用
   │ 子课题A │   │ 子课题B │   │ 子课题C │   │ 子课题D │      并行执行
   └─────────┘   └─────────┘   └─────────┘   └─────────┘
```

**并行价值**：N 个子任务的墙钟耗时 ≈ `max(单个耗时)` 而非 `sum(全部)`。
子任务彼此独立、无共享状态，所以能安全地放进线程池并行（LLM 调用是 I/O 密集，
`ThreadPoolExecutor` 足够，GIL 不构成瓶颈）。

## 三、代码结构

```
作业-subagent并行/
├── README.md
├── requirements.txt
├── src/
│   ├── llm_client.py     # DeepSeek 客户端（线程安全，多 subagent 复用）
│   ├── subagent.py       # SubAgent：执行单个子任务，记录耗时/线程等元信息
│   ├── orchestrator.py   # 主 Agent：plan → dispatch_parallel → synthesize
│   └── main.py           # CLI 入口：跑任务 + 甘特图 + 并行/串行对比 + 存档
└── outputs/
    └── last_run.json     # 最近一次运行的完整结果（子任务、各子结果、计时）
```

## 四、如何运行

```bash
export DEEPSEEK_API_KEY=你的key        # 环境里已配置则可跳过
pip install -r requirements.txt
cd src
python main.py                         # 默认示例任务
python main.py "你的复杂任务"           # 自定义任务
python main.py --serial "你的任务"      # 额外真实串行重跑一遍做实证对照
```

## 五、实测效果（默认任务：2024 中国新能源汽车行业市场调研）

主 Agent 自主拆出 4 个子任务并并行下发：

```
[主Agent] 拆解出 4 个可并行子任务：
    - 子1: 市场规模与增长分析
    - 子2: 主要厂商竞争格局分析
    - 子3: 政策与补贴导向分析
    - 子4: 出海与未来趋势分析

[主Agent] 并行下发 4 个 subagent（线程池 max_workers=5）...
  ▶ [子1·subagent_0] 开始 ... ▶ [子2·subagent_1] 开始 ...
  ▶ [子3·subagent_2] 开始 ... ▶ [子4·subagent_3] 开始 ...   ← 4 个同时启动

=== 并行时间线（甘特图，越重叠说明并行度越高）===
子1 |███████████████████████████             |  3.6s  市场规模与增长分析
子2 |████████████████████████████████████████|  5.2s  主要厂商竞争格局分析
子3 |████████████████████████████████        |  4.2s  政策与补贴导向分析
子4 |█████████████████████████████           |  3.8s  出海与未来趋势分析
```

| 指标 | 数值 |
|---|---|
| 子任务数量 | 4 |
| **并行墙钟耗时** | **5.2 s** |
| 串行理论耗时（各子之和） | 16.79 s |
| 真实串行重跑耗时（`--serial` 实测） | 17.8 s |
| **实测加速比** | **3.42x** |

> 加速比 ≈ 子任务数 × 各子任务耗时的均衡度。子任务越多、耗时越接近，
> 并行相对串行的优势越大（理论上限 = 子任务数）。

最终，主 Agent 把 4 份子结果汇总成一份结构化的市场调研报告（见 `outputs/last_run.json`
的 `final_report` 字段）。

## 六、关键设计点小结

1. **动态拆解，而非硬编码拓扑**：拆几个子任务、分别是什么，由主 Agent 的 LLM 依据
   具体任务决定 —— 换个任务无需改代码。
2. **subagent 无共享状态**：每个 subagent 独立完成一个自足指令，保证并行安全。
3. **并行编排**：`ThreadPoolExecutor` + `as_completed`，谁先完成先收谁的结果。
4. **可度量**：内置甘特图 + 并行/串行对照，把"并行完成多项工作"的收益量化出来。
5. **健壮性**：LLM 调用带指数退避重试；单个 subagent 失败不影响整体，会在汇总时标注。
